========================================================================================================
Conclusions
========================================================================================================
- All 49 queries run by more than one flavour returned identical hit
  counts, so the latency table compares implementations that agree on the answer.
- Demand: 0.0% of queries found every pair column already built. The rest
  pay for FK loads and a build on the query thread, so the cold share is what the
  build and from-side sections below are really measuring.
- Build cost: 2,499 ms across 195 rounds, 9.3% of it persisting.
  Computing the models dominates: the FK column walk and term resolution, not
  the sidecar write, is where the build time goes.
  Every build runs inside a query, so the whole cost lands on the query path and is
  what searcher warming would remove (9.1).
- A-priori pruning (7.2) dropped 32.2% of candidate pairs before opening a single column.
  This log does not say how many of those pairs were simply empty (mapping no
  from doc) rather than missed by the query's from matches.
