========================================================================================================
Conclusions
========================================================================================================
- 1 of 1,699 queries run by more than one flavour came back
  with different hit counts. Either a join is wrong, or the index changed between
  the two runs of that query -- this benchmark indexes while it searches, so a few
  scattered disagreements are expected and a systematic bias by one flavour is not.
  Flavours differing from the majority: aijoin x1
  First example: size_s:("XS" OR "13" OR "9" OR "36W34L") | fq=brand:("Granite" OR "Solace" OR "Nimbus")
    aijoin       86,136
    join         86,133
    joinglob     86,133
    joinnum      86,133
    jointop      86,133

- Demand: 98.5% of queries found every pair column already built. The rest
  pay for FK loads and a build on the query thread, so the cold share is what the
  build and from-side sections below are really measuring.
- Build cost: 12,618 ms across 102 rounds, 56.9% of it persisting.
  Roughly even between computing models and persisting them, so neither alone
  is the build's bottleneck.
  Every build runs inside a query, so the whole cost lands on the query path and is
  what searcher warming would remove (9.1).
- From side: 109 of 132 FK loads re-loaded a segment already
  loaded earlier in the log. Nothing caches the FK column across queries, so every
  query that still misses a pair pays the full hash build again.
- A-priori pruning (7.2) dropped 44.4% of candidate pairs
  before opening a single column. This is the level doing the visible work.
- Approximation (5.3): A-hat covers a median 100.0% of the parent segment.
  It is nearly uninformative, so almost every non-matching parent that the
  sibling filter admits is a false positive -- the regime where the paper
  predicts document-level pruning pays least, and the argument for n-range
  approximation rather than a single interval.
- Document-level pruning (7.3): laziness held on 36.5% of contexts with live
  columns, leaving 16.4% of surviving columns unopened.
  Most contexts converged, i.e. the lazy variant degenerated to the eager
  one (Algorithm 1) on the first candidate it could not confirm -- exactly the
  worst case described in 5.3.
- Caveat: the free-hit rate above is computed over converged contexts only,
  because a context that never converges emits no evt=done line and its final
  counters are never logged. Converged contexts are precisely the ones where
  laziness failed, so that rate is a pessimistic bound, not an average.
